# TFIT — Design System

## Identity — "TFIT Gold" (revised)

Not a SaaS dashboard, not a "generated by AI" app. Reference quality bar: Apple Design, Nike Training Club, Strava, Whoop, Oura, Freeletics — for craft, motion, and retention mechanics only, never copied directly. The identity was revised again to match the official TFIT logo (black background, gold/white wordmark) the user provided — replacing the earlier "Performance Tech" electric mint/blue palette with a black/gold/white one, same underlying token structure:

- **Tone**: confident, premium, data-forward — now closer to a premium/luxury athletic brand (think a black-and-gold membership card) rather than a biometric-wearable aesthetic, while keeping the same data-forward information design.
- **Dark is the flagship surface**, not a toggle-able alternative: near-black backgrounds (`#0A0A0A`, with `sunken` surfaces at true black `#000000`) with a rich gold→deep-gold gradient accent (`#F2D272` → `#B8860B`, flat accent `#D4AF37`) paired with white as the secondary accent — used deliberately for CTAs, data visualization, and glow accents, matching the logo's own gold/white-on-black relationship. Gradients and glow shadows are used with intent (primary actions, score/progress displays, unlocked-achievement rings), not on every surface.
- **Feedback colors were shifted to stay distinct from the new gold accent**: `warning` moved from an amber/gold tone (which would now be nearly indistinguishable from `accent.primary`) to a clear orange (`#FF8A3D` dark / `#C2540E` light); `success` (green) and `danger` (red) are unchanged, since neither read as ambiguous against gold.
- **Every animation has a job**: state change, causality (this action produced this result), or spatial continuity. No animation exists to "look modern."

## Tokens (`packages/ui/src/tokens`)

Token categories, defined once and consumed everywhere in the mobile app. The web admin panel does not consume `@tfit/ui` (a React Native package, not usable in a DOM app) — it has its own from-scratch CSS token system (`apps/admin/src/app/globals.css`) with an intentionally distinct "Moderation Command Center" identity: dark and information-dense like the mobile app, but built from plain CSS custom properties rather than shared components, and using the brand's accent gradient only for the primary action, active tab, and pending-status badge rather than throughout. See the Master Design Script status section below for what that redesign covers.

- `color` — semantic tokens (`color.background.base`, `color.text.primary`, `color.accent.primary`, `color.accent.secondary`, `color.feedback.danger`, `color.gradient.primary`/`color.gradient.hero`, ...), each with a light and dark value. Components reference semantic tokens, never raw hex. `gradient.primary` is the `[accent.primary, accent.secondary]` pair used by `Button`'s primary variant, `ScoreBar`'s fill, the FAB, and `RadialGauge`'s ring — one token pair, applied consistently, rather than each component picking its own gradient.
- `typography` — a type scale (display, title, headline, body, caption, label) with explicit line-height and weight, not ad hoc font sizes per screen.
- `space` — a spacing scale (4px base unit) used for all padding/margin/gap.
- `radius` — a small set of corner radii (sharp, soft, pill) used consistently by component role, not per screen.
- `elevation` (`packages/ui/src/tokens/elevation.ts`, added in the Master Design Script pass) — a formal 3-level neutral shadow scale (`sm`/`md`/`lg`), distinct from `Surface`'s accent-tinted `glow` prop: elevation is physical depth (neutral), glow is a highlight moment (accent-colored). Both are used sparingly, not on every card.
- `motion` — duration/easing tokens: `fast` (120ms, microinteractions), `standard` (220ms, transitions), `emphasis` (360ms, larger layout shifts), `celebration` (800ms, achievement/PR/level-up — added in the Master Design Script pass to give celebration moments their own explicit duration instead of reusing `emphasis`).
- `text.muted` and `background.pressed` — added alongside `elevation`/`celebration` to round out the token set the Master Design Script's component list needs (a third text tier between secondary and disabled; a momentary pressed-state surface tone distinct from the permanently-recessed `sunken`).

## Theming

Dark mode is a first-class design, not an inverted palette: separate contrast/elevation decisions for dark surfaces (lower-saturation accents, deliberate elevation via subtle luminance steps rather than shadows, which don't read on dark backgrounds). Implemented via a `ThemeProvider` in `packages/ui` that resolves tokens from the OS color scheme with an explicit user override in `user_preferences`.

## Motion & 3D budget (master spec §28/§32)

- Reanimated for UI-thread microinteractions (set completion, XP gain, streak flame, level-up, like-button burst) — implemented in Phase 7 for the rest timer, XP/FIT Score bars, achievement unlock celebration, and badge entrance animation.
- `react-native-svg` (+ Reanimated's `useAnimatedProps`) for circular/vector data-viz — the rest-timer ring (Phase 7) and its generalization, `RadialGauge` (a reusable gradient-stroke ring for any 0-100 score: level progress on Home, FIT Score on Evolution), rather than pulling in Skia. Skia stays reserved for actual exercise 3D/illustrative demonstrations, which remain deferred pending real content and an admin content-upload pipeline (neither exists — Phase 9's admin panel shipped only a reports queue, docs/ARCHITECTURE.md); no placeholder 3D work was built to fill a phase number.
- `expo-linear-gradient` for rectangular/pill gradient fills (buttons, the FAB, hero header backgrounds, achievement-badge rings) — `react-native-svg`'s gradients are used specifically for the circular gauges since that's SVG-native; `expo-linear-gradient` is the simpler, correct tool for gradient `View` backgrounds and doesn't require hand-rolling `<Rect>` shapes.
- Every animated component ships a reduced-motion fallback and is profiled on a low-end Android target before merging (performance budget, not a suggestion). The Phase 7 components (rest-timer ring, progress bars, achievement entrance, celebration modal, like-button burst) all check `theme.reducedMotion` and snap instead of animating when it's on.

## Accessibility (Phase 9)

Every icon-only or ambiguous-purpose `Pressable` app-wide carries `accessibilityRole="button"` and a Portuguese `accessibilityLabel` — modal close buttons, like/comment/menu icons, reorder chevrons, state toggles (labels reflect current state, e.g. "Curtir"/"Descurtir"). `Pressable`s wrapping already-self-descriptive visible text (a `Button` labeled "Salvar", a settings row whose own text names the destination) are deliberately left as-is — mechanically labeling everything would be noise for a screen reader, not help. Minimum touch targets get `hitSlop={8}` where an icon's hit area would otherwise fall under ~44 logical pixels. Not yet audited: color contrast ratios against WCAG AA (the token palette was designed by eye, not measured) and screen-reader flow-order testing on a real device — both worth a dedicated pass, not folded into this one.

## Screen state contract

Every screen must define, before implementation (master spec §57): loading, success, empty, error, and offline (where applicable) states. No screen ships with only the happy path.

## Navigation shape (master spec §49)

Bottom tab bar: `Home`, `Treinos`, `Personal`, `Feed`, `Perfil`, plus a floating `+` action button overlaid on the bar (start workout / check-in / post) rather than consuming a tab slot. `Personal` (the trainer directory, Phase 5) was added to the original 4-tab plan at the user's request; `Feed` (Phase 6, social) fit into the existing 5th slot without needing a 6th tab. 5 tabs plus an overlaid FAB is still within normal mobile bottom-nav bounds.

## Component philosophy

- Primitives (`Text`, `Surface`, `Button`, `Stack`) in `packages/ui/src/primitives`, token-driven, no screen-specific styling leaking in. `Surface` and `Button` gained `glow`/gradient treatments in the Performance Tech revision — still primitives (no screen-specific logic), just with a richer visual vocabulary than the original flat-fill design.
- Composed components (`ScoreBar`, `RadialGauge`, `CircularTimer`, ...) live app-side in `apps/mobile/src/components`, built from primitives, added when the screen that needs them is actually built — not speculatively.

## Master Design Script (in progress)

The user handed over a 102-section design brief ("TFIT — MASTER DESIGN SCRIPT / Performance Intelligence / Fitness OS") calling for a full visual/interaction redesign plus a 3D exercise-demonstration system, with its own prescribed execution order (Foundation → Core Components → Core Experience → Gamification → Social → Professional → Admin). Work is proceeding in that order, one chunk per session rather than all at once (the brief's own §61 says not to attempt everything simultaneously). Status:

- **Foundation** ✅: `elevation` and `celebration`-duration tokens added (above), plus `text.muted`/`background.pressed`.
- **Core Components** ✅ (first batch): `Skeleton` (shimmering loading placeholder — replaces bare spinners wherever the eventual layout is known), `EmptyState` and `ErrorState` (consolidate what used to be ad-hoc per-screen empty/error blocks into one consistent shape+microcopy pattern), `Badge` (numeric/dot indicator — replaces the hand-rolled unread-count view in the feed header), `IconButton` (icon-only pressable with enforced `accessibilityLabel` and a consistent pressed-state), `BottomSheet` (generic sheet shell — `QuickActionSheet`/`PostActionSheet`/`ReportModal` were each independently reimplementing the same Modal+backdrop+Surface pattern; they now all share one), `ToastProvider`/`useToast` (transient non-blocking confirmations — "Post publicado", "Treino salvo", "Perfil salvo" — per the brief's "no traditional alerts for routine confirmations" principle, §14).
- **Wired into real screens** (not built speculatively): Feed (skeleton loading, empty/error states, badge), Evolution (skeleton loading, error state), Home (contextual subtitle under the greeting per §8 — adapts to whether the user has a plan, has a workout today, or has an active streak), post creation / manual workout builder / professional profile save (toast confirmations).
- **Found and fixed while wiring**: the Home hero gradient panel is deliberately dark-navy in *both* light and dark theme (a fixed-dark hero treatment, not theme-relative), but its text was using `color="inverse"` — a token that flips meaning per theme and would render near-black-on-navy (functionally invisible) in dark mode. Added dedicated `gradient.heroText`/`gradient.heroTextMuted` tokens instead of a theme-relative one.
- **Core Experience** ✅ (§61's Fase 3 — Onboarding, Home, Treinos, Modo treino, Descanso, Resultado do treino, Evolução):
  - `AISignal` (abstract pulsing 3-dot indicator) and `AIGenerationSequence` (narrated, cycling sub-steps for the opaque `/api/training/generate` call — holds on its last step rather than looping or faking completion) give the AI-generation moments an honest sense of progress instead of a bare spinner. Wired into the Treinos empty-state generator and into a new onboarding→generation flow (`onboarding/generating.tsx`): a staged personalized-summary reveal ("Seu objetivo é...", "Você treina Nx por semana...") auto-transitions into generation, then branches to a ready/retry screen — onboarding data is saved before this screen is ever reached, so a failed generation never traps the user.
  - Onboarding step transitions (§56): steps now animate in with `SlideInRight`, gated by `reducedMotion`; `StepProgress` redrawn as filled/hollow dots (current step slightly larger) instead of thin bar segments.
  - Modo treino (set logging) restyled around a large centered rep-count input inside a raised card, rather than a plain two-field form.
  - Descanso (`RestTimer`) gained last-5-seconds color/pulse emphasis on the countdown ring and digits, plus an optional "next set" preview card.
  - Resultado do treino (post-workout summary) now shows real stats — duration (computed from the server's `session.startedAt`/`completedAt`, not the client clock), total sets, exercise count, XP earned, current streak, and new-PR count — instead of a single completion sentence.
  - Evolução: weight now shows a real trend delta ("↓ 0.8 kg · últimos N dias", computed from the actual tracked-weight history) instead of a bare current value; active goals show a current→target progress bar **only for `weight_target` goals**, where a genuine current value (latest tracked weight) and a genuine baseline (earliest tracked weight) both exist — `measurement_target`/`exercise_pr`/`custom` goals keep the plain title/type/date treatment because the progress response has no comparable current-value series for them, and fabricating one would violate the brief's "no invented data" principle.
- **Gamification** ✅:
  - **Level-up moment** (previously nonexistent — leveling up is a real, already-live mechanic that simply had no detection or visual feedback): `awardXp` (`apps/backend/src/lib/gamification.ts`) now compares the level implied by the user's XP total before and after each award, returning `leveledUp`/`newLevel` alongside the existing `xpAwarded`. `GamificationEventResult` (`packages/types/src/gamification.ts`) carries this to the client, and `GamificationCelebration` renders a distinct `LevelUpHero` (bigger gradient-ring badge with the new level number, level name, "VOCÊ SUBIU DE NÍVEL" label) above any XP/achievement content in the same celebration, with a slightly longer auto-dismiss so there's time to read it. Wired through checkin, workout-completion, and per-set (PR) XP awards — not through goal-achievement XP, which has no UI consumer yet and would've been speculative.
  - **PR celebration polish**: `GamificationCelebration` gained an `isNewPersonalRecord` prop — the per-set celebration in the workout session screen now shows a distinct "NOVO RECORDE PESSOAL" trophy label instead of a PR being indistinguishable from any other XP gain.
  - **Streak freeze indicator** (a real, already-returned field — `GamificationProfile.streak.freezesAvailable` — that had no UI anywhere, a gap noted while auditing this phase): the Home gamification card now shows the freeze count under the streak pill when the user has an active streak and at least one freeze available.
  - Achievements and Challenges screens moved from a bare `ActivityIndicator` spinner to the `Skeleton`/`ErrorState` pattern established in Fase 3 (shape-matched skeletons, explicit error state) for loading/error consistency across gamification screens.
  - **Noted but not changed**: Evolution's `currentStreakDays` (derived from daily check-in dates) and the gamification profile's `streak.current` (a separate freeze-aware state machine) are two distinct streak concepts that render almost identically (🔥 + day count) in two different places. Reconciling them is a data-model decision, not a visual one, so it wasn't touched in this pass — flagged for a future session.
- **Social** ✅ — an audit at the start of this phase found Feed was the only social screen using the `Skeleton`/`EmptyState`/`ErrorState` triad (from Fase 3); the other 8 social screens still used a bare `ActivityIndicator` for loading, plain `<Text>` for empty states, and in 5 of them (`(app)/perfil`, `notifications`, `follow-requests`, `blocked-users`, `profile/[handle]/connections`) had **no error-state handling at all** — a failed query silently rendered nothing useful. Brought all of them up to the same standard:
  - New shared skeletons — `PostCardSkeleton` (extracted from Feed's local one, now also used by post detail) and `UserRowSkeleton` (avatar + two lines, matches `UserRow`'s shape — reused for connections, notifications, follow-requests, blocked-users, and post-detail's comment list).
  - `post/[id].tsx`, `profile/[handle].tsx`, `profile/[handle]/connections.tsx`, `(app)/perfil.tsx`, `notifications/index.tsx`, `follow-requests/index.tsx`, `blocked-users/index.tsx`: each now has a shape-matched skeleton loading state, an `EmptyState` (with a meaningful icon, not just text) for its empty case, and an `ErrorState` for its error case.
  - `profile/[handle].tsx`'s post-grid empty state now distinguishes "this account is private" (lock icon) from "genuinely no posts yet" (image icon) — previously both were the same plain text block with only the message differing.
  - `PostCard`'s type-label icon (workout/achievement/PR/streak) was a single generic sparkles icon for all four; now each has its own icon (barbell, ribbon, trophy, flame) so the label reads as it's described rather than uniformly decorated.
  - No new social capabilities were added — this phase was consistency/polish only, in line with the brief's explicit prohibition (§50) on inventing chat, DMs, or anything not already part of the real feature set.
- **Professional** ✅ — the four professional-directory screens (`personal/index`, `personal/[userId]`, `personal/register`, `personal/menu`) had zero usage of `Skeleton`/`EmptyState`/`ErrorState` anywhere, and 3 of the 4 didn't check `isError` on their primary query at all. Brought up to the established standard, plus one real bug fix:
  - **Bug fixed**: `personal/[userId].tsx` conflated "still loading" with "professional not found" (`if (isLoading || !professional)` → spinner forever) — a bad/stale id or a deactivated professional showed an infinite spinner with no way out. Split into three explicit states: loading (skeleton), fetch error (`ErrorState`), and not-found (`EmptyState`, since it's a valid empty result, not a network failure).
  - `personal/index.tsx` (directory): shape-matched `Skeleton` loading (new `ProfessionalCardSkeleton`), `EmptyState`/`ErrorState`, pull-to-refresh added (previously the only social/feed-style list without it), and the hand-rolled avatar circle swapped for the shared `Avatar` component. The "É profissional? Cadastre-se aqui" banner — the closest thing to a CTA on this screen — gained a small accent-tinted icon badge instead of being visually identical to a plain list row.
  - `personal/register.tsx` and `personal/menu.tsx`: added skeleton loading and `ErrorState` for their profile/services queries — `register.tsx` previously treated a failed profile fetch as "no profile yet," which could show an empty registration form to someone who actually has a saved profile if the request merely failed transiently.
  - `menu.tsx`'s "Ocultar"/"Reativar"/"Remover" row actions gained `accessibilityRole`/`accessibilityLabel` (present on every other interactive element in the app, missing here) — kept as compact text actions rather than forcing them into the full-padded `Button` primitive, which would have been visually too heavy for an inline row.
  - No functional changes to the contact/services model — confirmed and preserved throughout: no payment, no booking, no in-app chat; contact stays external (WhatsApp/phone/Instagram/email links), matching the explicit product constraint ("like a menu, no payment, no intermediation").
- **Admin** ✅ — the whole app (4 pages, ~9 source files) had zero design system, zero dark mode, zero loading/empty/error states, and no components directory; it was plain default-browser-styled HTML with inline styles (`color-scheme: light`, off-white background, no icon library, no responsive handling). Rebuilt from scratch as a distinct "Moderation Command Center" identity rather than reusing `@tfit/ui` (a React Native package that can't run in a DOM app anyway):
  - New `apps/admin/src/app/globals.css`: a full CSS-custom-property token system (dark background tiers, text tiers, the brand's accent gradient used sparingly, status colors for pending/reviewed/dismissed, spacing/radius scales, a monospace stack for timestamps) plus component classes (`.shell`, `.card`, `.badge-*`, `.btn-*`, `.tab`, `.state-block`, `.skeleton`) — no Tailwind or component-library dependency added, in proportion to an app this small.
  - New `apps/admin/src/components/`: `Header` (brand + signed-in email + sign-out, present on every authenticated page — previously there was no way to sign out or switch accounts anywhere in the app), `StatusBadge`, `Tabs` (now shows a live count per status), `ReportCard` (clearer hierarchy, per-target-type icon), `EmptyState`.
  - `reports/loading.tsx` (skeleton) and `app/error.tsx` (error boundary with retry) added — neither existed before; a failed query previously fell through to Next's default unstyled error page.
  - `not-authorized` gained a "Entrar com outra conta" sign-out action — previously a dead end if the wrong account was signed in.
  - `<ClerkProvider appearance>` themed to match, so the Clerk-hosted sign-in widget doesn't look like a visual non-sequitur next to the rest of the app.
  - **One functional addition, using existing infrastructure rather than inventing new scope**: `updateReportStatus` now writes to the existing (previously unused by this app) `auditLogs` table — who reviewed/archived a report, and when — since a "Command Center" without any moderation trail didn't earn the name. No UI to browse that log was built (out of scope for this pass); the data is just no longer silently absent.
  - Everything else is unchanged: `requireAdmin()`'s email-allowlist gate, `listReports()`'s query/shape, the reviewed/dismissed-only action set, no user/content management, no deletion action — per the explicit scope boundary (`docs/FUNC.md` §16), this stayed a reports queue, just one that finally looks and behaves like a real tool.

All seven phases of the Master Design Script's own execution order (Foundation → Core Components → Core Experience → Gamification → Social → Professional → Admin) are now complete. The one open item from the original brief is the separately-scoped 3D exercise-demonstration system (§64-102), which needs an asset/licensing decision from the account owner before any implementation can start (see the note below) — everything else the brief asked for has shipped.

### The 3D exercise-demonstration system (§64-102 of the brief) — scope note

The brief's own quality bar for this ("anatomically plausible," "semi-realistic," rigged human characters with full biomechanical animation across dozens of exercises, camera controls, muscle highlighting, equipment interaction) is **3D art and animation production work — modeling, rigging, keyframing by a 3D artist/animator — not something achievable by writing code.** There's no licensed asset library in this project and no budget/sourcing decision has been made for one. Attempting a placeholder version (simple geometric/primitive figures) would fail the brief's own explicit principle of not shipping something that looks like a template or a cheap boneco — so nothing was built here rather than build something that would need to be thrown away. This needs the account owner's decision on direction (license a commercial 3D fitness-animation library, commission custom assets, or scope down to 2D animated diagrams as a realistic interim) before any implementation work starts — see the conversation for the options laid out.
